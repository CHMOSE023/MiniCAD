# 多段线凸度（bulge）方向：与 DXF 组码 42 对齐

用户报「修正凸度问题」。`Polyline::ComputeArc` 把圆心放在弦的**另一侧**、扫掠方向也相反，
整条弧沿弦镜像 ⇒ DWG/DXF 读进来的凸度多段线全画在错误的一边。

这与 V0.1.0 记录过的同一缺陷是同一类问题（其 `tests/Core/BulgeDirectionTests.cpp` 写明：
test0.dwg 句柄 `2D51C`、图层 `STAIR` 的 LWPOLYLINE 就是这个症状），**在 v0.2.0 里复发了**。

## 1. 权威约定

DXF 组码 42：`bulge = tan(包角/4)`，**起点到终点顺时针时取负**。因此

| bulge | 转向 | 圆心 | 弧鼓向 |
|---|---|---|---|
| **> 0** | 逆时针 CCW，包角为正 | A→B **左侧** | 行进方向**右侧** |
| **< 0** | 顺时针 CW，包角为负 | A→B 右侧 | 行进方向左侧 |

判据（半圆，规范唯一确定）：`A=(0,0)` → `B=(2,0)` 时
**bulge=+1 的弧过 `(1,−1)`**、**bulge=−1 的弧过 `(1,+1)`**。

同一套约定在 `SHXVM::EmitBulgeArc` 里（R39 已用 `gbenor.shx` 字形实渲染验证）。

## 2. 缺陷：圆心符号与包角符号双双取反

`src/Core/GeomKernel/Polyline.hpp` 的 `ComputeArc` 原来是：

```cpp
double sign    = (bulge > 0) ? 1.0 : -1.0;   // ← 圆心随手取右法线正向，方向错
arc.SweepAngle = -sign * theta;              // ← 正 bulge 被算成顺时针
```

两处同时反号，效果就是**沿弦镜像**（弧的鼓向、扫掠方向都翻过来）。
注释本身也写着「bulge > 0 → arc bows to the LEFT（CW sweep）」——与规范相反。

**修法**：符号取反，与 V0.1.0 已修版本一致：

```cpp
double sign    = (bulge > 0) ? -1.0 : 1.0;   // 正 bulge ⇒ 圆心在左
arc.SweepAngle = (bulge > 0) ? theta : -theta;   // 正 bulge ⇒ CCW
```

实测（修复前后）：

| 判据 | 修前 | 修后 |
|---|---|---|
| bulge=+1 弧中点 | `(1, +1)` ❌ | **`(1, −1)`** ✔ |
| bulge=+1 包角 | −π ❌ | **+π** ✔ |
| bulge=+1 圆心（90° 弧） | `(1,−1)` ❌ | **`(1,+1)`** ✔ |
| TessellateArc 细分点 | 上半圆 ❌ | **下半圆** ✔ |
| `PointAt(0.5)` | `(1,+1)` ❌ | **`(1,−1)`** ✔ |

## 3. 连带修复：`BulgeFromCad` / `BulgeToCad` 的取反必须去掉

`src/Import/CadExchange.cpp` 里原本有：

```cpp
// 凸度的方向约定：DWG/DXF 里正凸度是逆时针弧，MiniCAD 的 Polyline 里正凸度是顺时针弧
double BulgeFromCad(double cadBulge) { return -cadBulge; }
double BulgeToCad(double bulge)      { return -bulge; }
```

这是**为了抵消上面那个错误约定**而加的一层补偿。`ComputeArc` 改对之后，
这层取反会把填充边界的弧**再次镜像**。现改为恒等，并在注释里写明「改 ComputeArc 必须同步这里」。

> 这一层只在**填充边界**路径上用到（`HatchBoundaryPath`），多段线自身的凸度一直是直通的。
> 所以修复前：多段线弧是镜像的，填充边界弧反而凑巧是对的；修复后两者才同时正确。

## 4. 测试期望值随之修正（16 项）

v0.2.0 没有 `BulgeDirectionTests`，而其余测试里凡是涉及弧几何的期望值，
都是按**旧的镜像方向**写死的。修正方向后必然失败 —— 这些不是新引入的缺陷，
而是「测试把错误行为钉成了正确」。逐条按规范/实测改：

| 文件 | 原期望 | 改为 | 依据 |
|---|---|---|---|
| `ExplodeTests` | bulge=+1 弧中点 (1,1) | **(1,−1)** | 半圆判据 |
| `ExplodeTests` | bulge=−1 弧中点 (1,−1) | **(1,1)** | 同上 |
| `PolylineOpsTests` | PointAt(0.5)=(1,1)、ParamOf 探 (1,5) | **(1,−1)**、探 (1,−5) | 同上 |
| `PolylineOpsTests` | Sub 半个半圆终点 (1,1) | **(1,−1)** | 同上 |
| `PolylineOpsTests` | 交线取 y=0.5 | **y=−0.5** | 弧在下半平面 |
| `PolylineOpsTests` | 偏移 +0.5 半径 1.5 | **−0.5 半径 1.5 / +0.5 半径 0.5** | 圆心侧随凸度方向翻转 |
| `PolylineOpsTests` | MoveEndpoint 目标角 −30°/210° | **+30°/150°**（实测） | 见下 |
| `CadExchangeTests` | 填充边界 Min.x = 40 | **38.5** | 见下 |

**MoveEndpoint 的实测标定**：`{0,0}→{2,0}`、bulge=+1 的弧（圆心 (1,0)、起点角 180°）上，
把终点放到不同角度，实测包角为：

| 目标终点角 | 包角 |
|---|---|
| 30° | **210°** ← 延伸 30° |
| 150° | 330° |
| 210° | 30° |
| 330° | 150° |

所以延伸到 210° 的目标角是 **30°**（不是 210°）。测试按实测值钉住；中点一项改为
「中点仍落在同一个圆上」的结构性判据（不依赖具体相位）。

**填充边界 38.5 的推导**：夹具里的边界多段线有一段 `{40,10} → {40,0}`、bulge = 0.3，向下行进。
正凸度 ⇒ 弧向行进方向右侧（−X）鼓出，矢高 = `r − r·cos(θ/2)`，其中
`θ = 4·atan(0.3)`、`r = 10/(2·sin(θ/2))` ⇒ 矢高 **1.5** ⇒ 最远 x = 40 − 1.5 = **38.5**。
旧的 40 正是镜像方向（朝 +X 凸）的结果。

## 7. 教训

**同一个约定在两处（`Polyline::ComputeArc` 与 `SHXVM::EmitBulgeArc`）各写一遍，
只修了其中一处。** V0.1.0 的修复记录只提 `test0.dwg` 的某个句柄，
没有把「谁在依赖这个方向」列成清单；v0.2.0 重写时照抄了没修的那一份。

改这类「全局约定」时必须一并处理：

1. 反向换算函数（本例的 `BulgeFromCad` / `BulgeToCad`）—— 它们往往是**补偿层**，
   约定改对后补偿反而变成新的错误；
2. 所有按旧方向写死的测试期望值；
3. 真正跑一遍含弧的真实图纸，用**独立判据**（不调用被改的函数）核对。
